## 实现系统级"正在播放"媒体会话（OS Media Session）

用户问酷狗之类播放器在任务栏/锁屏显示"正在播放"是怎么实现的。解答：
- 这是 OS 级 Media Session 机制；Windows 走 SMTC，macOS 走 MediaRemote，Linux 走 MPRIS
- 而且是双向的：系统也会把媒体键/任务栏控件事件回传给程序

### 实现（用 souvlaki 跨平台封装）
- 新增依赖 `souvlaki = "0.8"`（内部封装 windows/macos/linux 三套后端，代码跨平台）
- 新增 `src/media_session.rs`：封装 `MediaSession`（持有 souvlaki::MediaControls）
  - `new(event_tx)` 创建会话并把系统事件通过 mpsc channel 转发出去
  - `set_metadata(title, artist, album, cover_path)` → 封面转 file:// URL
  - `set_playback(playing)` → Playing/Paused
- `MusicPlayer` 新增字段 `media: Option<MediaSession>`
- `new()` 中创建会话 + 启动后台循环：`Arc<Mutex<Receiver>>` + `cx.background_spawn` 阻塞 recv，
  收到事件后 `this.update` 调用 `handle_media_control`
- 重构 `play_pause`→`toggle_playback`、`next`→`next_track`、`prev`→`prev_track`（供 UI 和系统键共用）
- 新增 `handle_media_control`（分发 Play/Pause/Toggle/Next/Previous/Stop）
- 新增 `sync_media_session`：切歌/暂停/封面提取完成时同步状态到系统
- `play()` 中播放开始 + 封面提取完成两处调用 `sync_media_session`

### 关键注意
- souvlaki 0.8 的 `PlatformConfig` 在 Windows 需要 `hwnd: Option<*mut c_void>`，传 `Some(null_mut())` 即可（进程级 SMTC）
- `attach` 闭包返回 `()`（不是 Result）；`MediaMetadata` 字段是 `Option<&str>`
- `MediaControls` 必须在 GPUI 主线程创建（`new()` 中创建，与 load_music_folder 的 cx.spawn 模式一致）

### 修改文件
- Cargo.toml（加 souvlaki）
- src/media_session.rs（新）
- src/main.rs（media 字段、事件循环、处理函数）

## Windows 构建环境坑（重要，已踩，可复现）

本机在 WorkBuddy 沙箱 bash 里 `cargo build` 链接阶段会失败，根因是 PATH / LIB 顺序：

1. **GNU `link` 抢占 MSVC `link.exe`**：沙箱 Git Bash 的 PATH 里 `/usr/bin/link`（GNU coreutils）
   排在 MSVC `link.exe` 前面，rustc 调链接器时实际跑了 GNU `link`，报错
   `link: missing operand after '\377\376'` / `Try 'link --help'`（这是 GNU link 输出，不是 MSVC）。
   - 修法：构建前把 MSVC bin 目录前置
     `export PATH="/c/Program Files/Microsoft Visual Studio/2022/Community/VC/Tools/MSVC/14.39.33519/bin/Hostx64/x64:$PATH"`

2. **缺 LIB 导致 LNK1181**：仅前置 PATH 还不够，会报
   `LNK1181: cannot open input file 'legacy_stdio_definitions.lib'`（以及 kernel32/user32 等裸 lib 找不到），
   因为没设 Windows SDK / MSVC 的 LIB 搜索路径。需同时设置：
   ```
   export LIB="C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Tools\MSVC\14.39.33519\lib\x64;C:\Program Files (x86)\Windows Kits\10\Lib\10.0.22000.0\ucrt\x64;C:\Program Files (x86)\Windows Kits\10\Lib\10.0.22000.0\um\x64"
   export INCLUDE="C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Tools\MSVC\14.39.33519\include;C:\Program Files (x86)\Windows Kits\10\Include\10.0.22000.0\ucrt;C:\Program Files (x86)\Windows Kits\10\Include\10.0.22000.0\um;C:\Program Files (x86)\Windows Kits\10\Include\10.0.22000.0\shared"
   ```
   - 注：本机 `legacy_stdio_definitions.lib` 不在 Windows SDK 的 ucrt 里，而在 MSVC 的 `lib\x64`（上面 LIB 第一项已覆盖）。

3. **别用 `cmd //c "...vcvars64.bat"` 图省事**：双斜杠 `//c` 不被识别为 /c 开关，会进交互式不执行；
   单斜杠 `cmd /c` 又被沙箱安全策略拦截。最稳是在 bash 里直接 export 上述三个变量再 `cargo build --offline`
   （依赖已缓存，离线可编；在线 cargo 会卡在索引更新超时）。

4. **误命令 `>nul` 残留**：曾在引号内误用 `>nul`，在工程目录生成名为 `nul` 的文件（Windows 保留设备名）。
   普通 `rm`/`del`/PowerShell `Remove-Item` 都删不掉（拒绝访问 / 被 safe-delete 拦截）。
   已加进 `.gitignore`；若要物理删除需 `\\?\` 扩展路径 + 绕过沙箱 safe-delete（如 `python -S` 调 `os.remove`），本机暂不处理。
