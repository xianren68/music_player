- `uniform_list` 的 callback 签名是 `Fn(Range<usize>, &mut Window, &mut App)`，需要 `'static` 闭包
- 点击事件通过 `entity.downgrade()` + `entity.update(cx, |this, cx| ...)` 在 `&mut App` 上下文中处理
- 在 `&mut App` 上下文中 `entity.update()` 返回 `()`，不需要 `.ok()`

- 播放时提取封面并缓存到 `current_cover: Option<Arc<RenderImage>>`

### 关于 Windows 文件管理器封面

- 使用 Shell API（`SHGetFileInfo`）异步提取并利用系统缓存
- 我们的代码每次都要重新打开 MP3 文件解析元数据，没有缓存，所以慢

## 最终实现虚拟滚动（成功）

### 问题
- 之前用 `entity.downgrade()` + `move` 闭包的方式，uniform_list 不显示内容
- 原因：uniform_list 的 callback 签名是 `Fn(Range<usize>, &mut Window, &mut App)`，需要 'static 闭包

### 解决方案：cx.processor()

**关键 API**：`cx.processor()` 把 `&mut Context<T>` 转成 `impl Fn(E, &mut Window, &mut App) -> R + 'static`

```rust
uniform_list(
    "sidebar-virtual-list",
    total,
    cx.processor(move |this, range: Range<usize>, _window, cx| {
        // this: &mut MusicPlayer（每次渲染可见区域时获取最新数据）
        // range: 当前可见项的范围
        // cx: &mut Context<MusicPlayer>（可用 cx.listener() 创建点击回调）
        
        for ix in range {
            let item = find_list_item(&this.folders, &this.loading_folders, ix);
            // 渲染...
        }
    }),
).h_full()
```

### 实现要点

1. **`find_list_item()` 函数** - 根据 ix 在 folders + loading_folders 中查找对应项，返回 `ListItemRef` 枚举（带引用，避免克隆）

2. **闭包内通过 `this` 获取最新数据** - 不需要在外部克隆 folders/current/eq_phase，闭包内 `this.folders`、`this.current`、`this.eq_phase` 都是最新值

3. **`cx.listener()` 可用** - processor 闭包的第四个参数是 `&mut Context<MusicPlayer>`，可以直接用 `cx.listener()` 创建点击回调

4. **`.h_full()` 必须加** - uniform_list 需要明确的高度约束

5. **容器 `.min_h_0()`** - flex_1 容器需要 min_h_0 允许收缩

6. **简化 build_sidebar 签名** - 移除了 `current` 和 `eq_phase` 参数（闭包内通过 this 获取）

### 修改的文件
- `src/ui/sidebar.rs` - 完全重写，使用 cx.processor() + uniform_list
- `src/main.rs` - 简化 build_sidebar 调用（移除 current/eq_phase 参数）

## 封面颜色修复：JPEG → PNG

### 问题
用户反馈封面颜色不对（应该是粉色，显示成蓝紫色）

### 调试过程
1. 提取原始 FLAC 封面并保存为 PNG → 颜色正确（粉色/暖色调）
2. 保存 JPEG 缓存后重新加载为 PNG → 颜色也基本正确
3. 结论：**JPEG 编码/解码不是根本原因**

### 根因分析
- JPEG 使用 YCbCr 颜色空间，解码时需要转换为 RGB
- 不同解码器可能使用不同的转换系数（BT.601 vs BT.709/sRGB）
- GPUI 渲染管线可能假设纹理是 sRGB，但 JPEG 解码后的 RGB 可能不完全匹配
- 即使质量设为 95，JPEG 的有损压缩仍可能导致轻微色偏

### 解决方案：改用 PNG 格式
- 缓存格式从 JPEG 改为 PNG
- PNG 是无损格式，保留完整的 RGBA 数据
- 避免 YCbCr → sRGB 颜色空间转换问题
- 文件名后缀从 .jpg 改为 .png
- cleanup_old_covers() 同时清理旧的 .jpg 和 .png 文件

### 验证结果
- 原始封面（FLAC 内嵌 PNG）：RGBA(153,110,111) 暗粉红 ✓
- 新 PNG 缓存：RGBA(153,110,111) 暗粉红 ✓
- 颜色完全一致，无偏差

## 封面颜色真正根因：RGBA → BGRA 通道交换

### 问题
PNG 格式修复后颜色仍然不对（粉色变蓝紫色）

### 调试过程
深入 GPUI 源码 `gpui-0.2.2/src/assets.rs`：
```rust
/// A cached and processed image, in BGRA format
pub struct RenderImage { ... }
```
`RenderImage::new()` **不做任何转换**，直接存储原始字节。

GPUI 的 `img.rs` 在从文件加载图片时会自动转换：
```rust
// Convert from RGBA to BGRA.
for pixel in frame.buffer_mut().chunks_exact_mut(4) {
    pixel.swap(0, 2);
}
```
但我们用 `RenderImage::new()` 直接创建，**绕过了这个转换**。

### 根因
- `image::Frame::new(rgba)` 传入的是 **RGBA** 数据
- GPUI `RenderImage` 期望 **BGRA** 格式
- R 和 B 通道被交换 → 粉色(153,110,111) → 蓝紫色(111,110,153)

### 修复方案
在所有创建 `RenderImage` 的地方，手动交换 R/B 通道：
```rust
let mut rgba = img.to_rgba8();
for pixel in rgba.pixels_mut() {
    pixel.0.swap(0, 2);
}
let frame = image::Frame::new(rgba);
```

### 修改的 4 处位置
1. `src/ui/sidebar.rs` - render_track_cover 列表封面
2. `src/main.rs` new() - 背景图加载
3. `src/main.rs` pick_bg_image() - 选择背景图
4. `src/main.rs` play() - 播放时加载主区域封面

### 技术要点
- `image` 0.25 的 `ImageBuffer` 没有 `as_raw_mut()`，用 `pixels_mut()` 替代
- `Rgba<u8>` 是元组结构体 `Rgba([u8; 4])`，用 `pixel.0.swap(0, 2)` 交换通道
